## 1. 프로그래밍 패러다임 비교

소프트웨어를 설계하고 구조화할 때 채택하는 세 가지 핵심 개발 철학의 특징입니다.

* **절차적 프로그래밍 (Procedural Programming)**:
  * 단순한 명령어의 순차적 흐름과 함수 호출을 중심으로 전체 코드가 돌아가는 순수 로직 실행 방식입니다.
  * 설계가 빠르고 단순하지만, 전역 변수 공유로 인해 규모가 커질수록 유지보수성이 저하됩니다.
* **객체지향 프로그래밍 (Object-Oriented Programming, OOP)**:
  * 실제 세계를 객체로 분할하고, 상태(데이터)와 행위(메서드)를 결합하여 모듈 단위로 작성하는 방식입니다.
  * 유지보수 및 확장성이 우수하지만, 구조 복잡성으로 인해 초기 설계 비용이 높고 런타임 오버헤드가 발생할 수 있습니다.
* **함수형 프로그래밍 (Functional Programming, FP)**:
  * 계산 과정의 상태 변경과 가변 데이터를 지양하고 순수 함수의 결합으로 문제를 푸는 수학적 접근법입니다.

## 2. 객체지향 프로그래밍(OOP)의 4대 핵심 원칙

### 1) 캡슐화 (Encapsulation)
데이터(변수)와 해당 데이터를 다루는 행위(메서드)를 하나의 클래스로 묶고, 내부 구현 세부사항을 외부에 은닉하여 보호하는 행위입니다.
* **UML 표기법**: 클래스 다이어그램에서 멤버의 접근 범위를 직관적으로 표시합니다.
  * `+` : public (어디서나 접근 가능)
  * `-` : private (클래스 내부에서만 접근)
  * `#` : protected (상속 또는 동일 패키지 접근)

### 2) 상속 (Inheritance)
부모 클래스의 공통 속성 및 메서드를 자식 클래스가 온전히 물려받아 새로운 특성을 확장 정의하는 원칙입니다.
* **주의**: 상속 구조가 너무 깊어지면 결합도가 높아져 설계 유연성이 하락합니다. 필요한 경우 객체를 멤버 변수로 포함하여 관계를 맺는 **컴포지션(Composition, 합성)** 사용을 고려해야 합니다.

### 3) 다형성 (Polymorphism)
하나의 시그니처나 계약이 상황에 따라 여러 개의 구체적인 형태로 발현되어 서로 다른 작동 방식을 가지는 특징입니다.
* **오버로딩 (Overloading - 정적/컴파일타임 다형성)**: 한 클래스 내에서 같은 이름의 메서드를 매개변수의 타입이나 개수를 다르게 하여 여러 개 중복 선언하는 것입니다.
* **오버라이딩 (Overriding - 동적/런타임 다형성)**: 상속받은 부모 클래스의 메서드를 자식 클래스 목적에 맞게 재정의하여 대체 구현하는 것입니다.

### 4) 추상화 (Abstraction)
구체적인 객체의 복잡한 정보 중에서 본질적이고 핵심적인 기능과 데이터만 간추려 모델링하고 세부 사항은 숨기는 원칙입니다.
* **추상 클래스 (Abstract Class)**: 구체적인 자식 구현체들의 공통 틀을 잡기 위한 반쯤 완성된 클래스로, 상속을 강제합니다. (UML상 명칭을 이탤릭체로 표기함)
* **인터페이스 (Interface)**: 행동 규약 및 스펙의 순수 모음집으로 다중 구현 및 느슨한 결합(Loose Coupling)을 보장합니다.

## 3. 함수형 프로그래밍 (FP)의 핵심 이론

* **순수 함수 (Pure Function)**: 동일한 매개변수가 들어가면 외부 상태(I/O, 파일 등)를 전혀 오염시키지 않고 항상 동일한 출력값만 정직하게 반환하는 함수입니다.
* **불변성 (Immutability)**: 데이터를 임의로 지우거나 덮어쓰지 않고, 연산 결과로 무조건 새로운 데이터 사본을 생성하여 대체 교체합니다.
* **일차 함수 및 고차 함수**: 함수를 일반 변수처럼 다른 메서드의 매개변수 인자로 담아 보내거나, 함수의 반환값 자체로 함수를 리턴하는 기법입니다. (코드의 선언형 표현력 극대화)

## 4. 소프트웨어 설계와 UML 다이어그램

UML(Unified Modeling Language)은 구조적 시각화 및 개발자 간 설계 의사소통 표준 문서 역할을 수행합니다.
1. **클래스 다이어그램 (Class Diagram)**: 클래스들의 관계(상속, 포함, 의존), 필드와 메서드를 보여주는 정적인 물리 구조 표현 다이어그램입니다.
2. **유스케이스 다이어그램 (Use Case Diagram)**: 시스템 외곽에서 사용자가 프로그램과 상호작용하여 얻어내는 기능 범위(요구사항)를 도식화합니다.
3. **시퀀스 다이어그램 (Sequence Diagram)**: 시간에 따라 객체들 간에 실시간으로 주고받는 메시지와 호출 절차를 표현하는 동적 다이어그램입니다.

## 5. 프로세스와 스레드 & 동기/비동기 개념

### 1) 프로세스 vs 스레드
* **프로세스 (Process)**: 운영체제로부터 메모리 공간과 실행 권한을 할당받아 실행 중인 프로그램 단위입니다.
* **스레드 (Thread)**: 하나의 프로세스 실행 환경 내부에서 자원을 공유하며 연산을 수행하는 더 작고 독립적인 실행 흐름 단위입니다.

### 2) 동기(Sync) vs 비동기(Async)
* **동기식 (Synchronous)**: 요청을 발송한 후 상대편의 응답이 전달될 때까지 연산을 정지하고 기다리는 구조로 순차적이지만 비효율적입니다.
* **비동기식 (Asynchronous)**: 요청을 보낸 뒤 응답을 마냥 기다리지 않고 다른 연산을 처리하다가, 작업 완료 이벤트나 콜백이 트리거되면 결과를 정돈하는 병렬 흐름 방식입니다.
